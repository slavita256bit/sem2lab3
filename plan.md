# План: добавление и удаление транспорта в лабораторной №3

Актуально после завершения TODO main: один массив Vehicle* objects[20], счётчик
занятых мест, список typeid для выбора класса. Ввод новых объектов работает до
заполнения массива, таблицы фильтруются внутри print_table и показывают исходный
номер объекта, изменение проверяет выбранный класс. Перед выходом все объекты
удаляются в обратном порядке. Удаление отдельного элемента остаётся будущей задачей.
Описания векторов и variant ниже относятся к предыдущим решениям.

Последняя реализация: без std::variant и собственных шаблонов для таблицы/ввода.
Шесть векторов конкретных классов хранят объекты по значению, по два начальных
объекта каждого класса. Общий код вывода и изменения получает временные адреса
выбранного класса; владение остаётся у исходных векторов. print_read_info возвращает
ссылку на объект, поэтому добавление и ввод объединены в одну строку.
У троллейбуса — ёмкость аккумулятора (кВт·ч) вместо напряжения сети.
При будущем удалении нужно удалять элемент соответствующего вектора значений,
затем заново формировать временный список адресов. Зависимости от первых шести
элементов общего вектора больше нет. Описания прежних решений ниже исторические.

Текущее уточнение: объекты теперь хранятся по значению в одном vector<Transport>,
где Transport — variant шести классов. Подсказки находятся в print_read_info
каждого класса. В main.cpp только main; выбор ввода/вывода выполняется std::visit.
Ни raw-, ни smart-указатели для хранения транспорта больше не используются.
При реализации удаления необходимо заменить выбор типа нового объекта по позиции
первоначальных шести элементов: создание должно работать и после их удаления.
Описания хранения ниже сохранены как прежние этапы плана и больше не актуальны.

Последнее изменение: по прямому пожеланию пользователя умные указатели,
свободные функции, общая таблица и write убраны. Сейчас используется один
vector<Vehicle*>; создание, ввод, выбор класса и освобождение объектов находятся
в main. Объекты освобождаются через delete в обратном порядке при выходе.
Вывод отдельных таблиц выполняется через <<, шапка — через print_header.
Меню: 1 — таблица класса, 2 — добавление, 3 — изменение, 0 — выход.
Рекомендации ниже о unique_ptr и отдельных свободных функциях больше не актуальны;
они сохранены как первоначальный план. Удаление через меню остаётся будущей задачей.

Статус: по последнему уточнению реализованы добавление через ввод и отдельный
выбор таблицы класса в главном меню. Удаление пока не реализуется. Ниже сохранён
общий план; его исходное описание отражает состояние до изменения меню.
Фильтр таблицы теперь задаётся std::type_info, поэтому для выбора класса
не требуется выбирать существующий объект. Выбор через старый пункт 8 убран.

Реализацию лабораторной №4, дерево, новую ветку и отдельный
проект на этом этапе не создавать. Перед реализацией повторно прочитать изменяемые
файлы: пользователь также правит их в CLion.

## Что есть сейчас

- Шесть локальных объектов создаются перед циклом конструкторами с параметрами.
- Внутри цикла заново собирается `std::vector<Vehicle*>` с их адресами.
- Таблица и выбор объекта используют порядок элементов вектора.
- Для изменения есть `change_field`, для ввода — перегрузки `>>` конкретных классов.
- Общая таблица содержит номер и имя класса. Отдельная таблица выбирает объекты
  точного динамического типа через `typeid`.

Просто добавлять в этот вектор адрес временной переменной нельзя: после выхода
из её области видимости указатель станет недействительным. Удаление указателя
из текущего вектора также не уничтожает исходный локальный объект.

## Хранение и время жизни

1. Использовать одну коллекцию `std::vector<std::unique_ptr<Vehicle>>`, созданную
   перед циклом меню. Все объекты принадлежат этой коллекции.
2. Начальные шесть объектов сохранить с текущими значениями, создавая их через
   `std::make_unique` и добавляя непосредственно в вектор. Не использовать
   initializer_list для unique_ptr: он требует копирования элементов.
3. Новый объект также создавать через `std::make_unique` нужного класса.
   Удаление выполнять одним `erase`: объект уничтожится через виртуальный
   деструктор Vehicle. При выходе оставшиеся объекты освободятся автоматически.
4. Не держать вторую коллекцию сырых указателей и не смешивать локальные объекты
   с объектами, которыми владеет коллекция. Не добавлять ручные new/delete,
   shared_ptr, собственный менеджер памяти или класс приложения.
5. Начальные данные создавать один раз. Возврат к меню сохраняет добавления,
   удаления и изменения; новый проход меню не восстанавливает удалённые строки.
6. После удаления номера снова соответствуют текущему порядку элементов, начиная
   с 1. Отдельное поле номера и постоянные идентификаторы пока не нужны.

Это запланированное изменение прежнего правила о vector<Vehicle*> и локальных
объектах: владение нужно для нового требования добавления и удаления. При реализации
обновить соответствующие актуальные пункты AGENTS.md, сохранив исторические разделы.

## Меню

Один цикл `while (true)` и обычный `switch` по номеру действия:

```text
1 — общая таблица
2 — добавить объект
3 — изменить объект
4 — таблица отдельного класса
5 — удалить объект
0 — завершить программу
```

- Общую таблицу показать при запуске, затем по пункту 1 и после добавления,
  изменения или удаления.
- Пункт 0 задаёт привычный вопрос «Завершить программу? (y/n):».
  При y/Y выйти; иначе вернуться к меню с сохранением данных. Для tolower
  передать символ через `static_cast<unsigned char>`.
- В выборе типа или объекта 0 означает отмену текущего действия.
- Для пустой коллекции выводить короткое сообщение. Добавление остаётся доступно.
- Проверять номера действий, типов и объектов. Проверки состояния cin/stream,
  fail/eof и повторный запрос при ошибке извлечения не добавлять.

## Добавление

1. Вывести шесть типов: Vehicle, CargoVehicle, DumpTruck, PassengerVehicle,
   Bus, Trolleybus; подписи оставить на русском с именем класса в скобках.
2. По выбранному типу создать объект и прочитать его одной строкой через
   существующий `operator>>` именно этого класса. Например, для самосвала:
   `Belaz 2024 40 25`. Подсказки остаются вне операторов.
3. Только после ввода передать объект в общий вектор через `std::move`.
   Не читать через Vehicle&: невиртуальная перегрузка базового класса
   не прочитает поля наследника.
4. Повторное добавление того же типа и одинаковых значений разрешить: коллекция
   хранит отдельные объекты, а удаление выполняется по номеру.

Шесть коротких ветвей выбора типа предпочтительнее фабрики, шаблона создания,
лямбд или цепочки dynamic_cast. Каждая ветвь содержит создание, подсказку,
ввод и добавление.

## Удаление и изменение

- Перед выбором показывать общую таблицу, чтобы пользователь видел актуальные
  номера. Проверять диапазон до обращения по индексу.
- Удалять только выбранный элемент через `erase`, затем показать результат.
  Лог деструкторов уже обеспечивает наглядность уничтожения наследника и баз.
- Изменение полей оставить через существующий виртуальный `change_field`.
  Пункт вывода отдельной таблицы перенести из списка полей в главное меню.
- После erase не использовать прежние индексы, итераторы или указатель на удалённый
  объект. Выбранный объект не хранить между действиями меню.

## Таблицы и демонстрация наследования

- `print_table` принимает коллекцию владеющих указателей по const&.
  При обходе использовать `const auto&`, не копируя unique_ptr.
- Существующий указатель `class_object` оставить невладеющим и передавать
  `objects[index - 1].get()` только на время вызова таблицы.
- В пункте 4 выбрать существующий объект: вывести все объекты точно такого же
  класса. Например, CargoVehicle не включает DumpTruck. При пустой коллекции
  сообщить, что выбирать пока нечего.
- Форматы, колонки и реализацию перегрузок >>/<< сохранить. Номер по-прежнему
  вычисляет вывод коллекции, он не является полем транспорта.
- Демонстрации static_cast/dynamic_cast/typeid выполнить один раз до меню на
  известных начальных объектах. После удаления не обращаться к фиксированному
  objects[4] и не хранить ссылки на первоначальные объекты.

## Как оставить код коротким

- В main оставить начальное заполнение, цикл меню и последовательность действий.
- Выбор типа с шестью ветвями вынести в одну обычную свободную функцию
  `add_object` в main.cpp. Это единственная необходимая новая вспомогательная
  функция; не добавлять interaction, demonstration, фабрику или отдельный модуль.
- Изменение, удаление и вызовы таблиц оставить короткими ветвями главного switch.
  Если при реализации они разрастутся, сначала сократить вложенность ранней
  отменой действия, а не создавать универсальные обёртки.
- Сохранить Allman, четыре пробела, snake_case, пустые строки между этапами,
  короткие русские комментарии и выравнивание правых комментариев в заголовках.
- Текущий закомментированный первоначальный ввод адаптировать к новой коллекции,
  чтобы он оставался рабочей альтернативой, без второго механизма хранения.

## Порядок реализации и проверки

1. Сначала зафиксировать текущее поведение ввода, изменения и таблиц.
2. Перевести хранение и print_table на unique_ptr, сохранив начальные данные
   и формат вывода. Проверить сборку до добавления новых действий.
3. Собрать единое меню, добавить создание и удаление; сохранить отмену,
   изменение полей, отдельные таблицы и подтверждение выхода.
4. Повторно просмотреть код на дублирование, лишние переменные, вложенность,
   висячие ссылки и несоблюдение пробелов или пустых строк.
5. Проверить добавление и ввод всех шести классов, несколько объектов одного
   класса, изменение добавленного объекта и точность отдельных таблиц.
6. Проверить удаление первого, среднего, последнего и единственного объекта,
   перенумерацию строк, отмену, неверный номер и добавление в пустую коллекцию.
7. Проверить возврат к меню после отказа от выхода: коллекция не сбрасывается.
   Проверить логи деструкторов и отсутствие повторного уничтожения.
8. Собрать GCC и Clang с предупреждениями, выполнить clang-tidy из CLion.
   Отдельно проверить сценарии добавления/удаления с AddressSanitizer и
   UndefinedBehaviorSanitizer.

добавлением через ввод и отдельным выбором таблицы. Лабораторную №4 выполнять позже
на основе согласованного результата лабораторной №3.
