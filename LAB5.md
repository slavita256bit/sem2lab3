## Условие в нормальной формулировке

Дополнить программу из лабораторных 3 и 4 обработкой исключительных ситуаций.
Сохранить предметную иерархию, шаблонный контейнер, основные операции и цикл меню.

1. Реализовать собственную иерархию исключений: общий базовый класс и производные

   ExceptionVvod/ExceptionFile/ExceptionContainer условные; разрешено улучшить их.
2. В базовом классе хранить int code. Конструктор принимает код, конструкторы
   производных классов вызывают конструктор базового.
3. Для сообщения предусмотреть char message[80], длину 80 вынести в #define.
   Сообщение можно разместить в базовом классе, чтобы не повторять его в наследниках.
   Буфер должен быть завершён нулём; 80 — байты вместе с завершающим нулём,
   а не гарантированные 80 русских букв в UTF-8.
4. Выделить непересекающиеся диапазоны кодов для разных категорий ошибок.
   Пример: 1–100 ввод, 101–200 файлы, 201–300 контейнер.
5. Проверять вводимые данные. При исправимой ошибке сообщать причину и повторять
   ввод до получения допустимого значения.
6. Строковые данные проверять по правилам конкретного поля. Для фамилии/страны
   приведён пример: только буквы одного выбранного алфавита, без цифр и символов.
   Это примеры для других вариантов; они не требуют добавлять туриста в наш проект.
7. Числа преобразовывать стандартным средством с проверкой результата, без atoi.
   Проверять не только диапазон, но и то, что введено именно число. Если границы
   диапазона вводятся пользователем, их ввод тоже должен проверяться.
8. Если есть дата, заранее сообщать её формат, проверять все части и допустимость
   календарной даты. В нашем транспорте есть год, полного поля даты сейчас нет.
9. Вынести повторяемую работу с проверенным вводом в собственный модуль h/cpp.

10. Ошибки, которые повтором ввода не исправляются, не зацикливать. Пример из

## Что видно на фотографиях

- Обсуждаются goodbit, eofbit, failbit, badbit и методы good/eof/fail/bad,
  rdstate/clear. Имена флагов нужно использовать вместо их числовых значений.
- В примере индекс проверяется внутри operator[]; при выходе за границы выбрасывается
  исключение. Проверки только в main недостаточно для защиты самого контейнера.
- Показаны try, throw, catch и повторный ввод после ошибки.
- На доске базовое исключение хранит код, у исключения ввода есть сообщение,
  производный конструктор передаёт код базовому.
- Фрагменты с фотографий не следует копировать буквально: catch лучше принимать
  по const ссылке, а clear() сам по себе не удаляет ошибочный текст из потока.
  Размытый консольный пример не используется как источник дополнительных требований.

Техническое уточнение: good() означает отсутствие всех флагов ошибки, eof() —
наличие eofbit, fail() — наличие failbit или badbit, bad() — наличие badbit.
Успешное извлечение последнего токена может одновременно установить eofbit.
Поэтому проверка !good() не равнозначна утверждению «значение не прочитано».

Последнее уточнение меню: номера объектов 0..size()-1, отмена выбора убрана.
0 — первый объект, 0 в главном меню — выход; классы и поля начинаются с 1.
Не возвращать пользовательскую отмену при добавлении обработки ошибок.

## Предлагаемая иерархия

```text
Error
├── InputError
├── FileError (отложен)
└── ContainerError
```

- Error: int code, char message[ERROR_MESSAGE_LENGTH]; ERROR_MESSAGE_LENGTH = 80
  через #define, get_code(), get_message() const noexcept.
- InputError: название поля, ввод которого не прошёл проверку.
- FileError: имя файла, с которым связана ошибка.
- ContainerError: int number — номер строки или другого аргумента ошибочной операции.

Для названий поля/файла можно использовать имеющийся String. Точное хранение этих
дополнительных данных выбрать при реализации с учётом простоты копирования ошибок.
Не создавать ещё десяток подклассов для каждой отдельной причины: её различает код.
Имена кодов задать enum class, не рассыпать голые числа по throw.
Конструкторы/деструкторы — в h, остальные методы — в cpp, по стилю проекта.
Деструкторы исключений не должны выбрасывать исключения. Перехват — const InputError&,
const ContainerError&, const Error&, более конкретные обработчики перед общими.

Сообщение в фиксированном буфере должно быть коротким и корректным в UTF-8.
Не допускать переполнения или разрезания многобайтной буквы при копировании.
Ограничение буфера сообщения не означает ограничение марки или имени файла 79 буквами.

## Проверенный ввод

Предлагается include/Input.h и src/Input.cpp, без нового слоя приложения.
Достаточно обычных функций read_int, read_double и read_brand в namespace input.
Новые шаблоны для пары числовых типов пока не нужны. В main.cpp остаётся только main.
Функции получают std::istream&, правила/границы и название поля для понятной ошибки.

Для чисел предлагается std::from_chars из <charconv>:

1. Прочитать одну строку в локальный String.
2. Преобразовать его в int или double.
3. Проверить код преобразования и то, что разобрана вся строка.
4. Для double дополнительно проверить std::isfinite: nan и inf не подходят
   для массы, объёма и ёмкости аккумулятора.
5. Проверить предметный диапазон.
6. При ошибке создать и выбросить InputError. Перехватить исправимую ошибку внутри
   функции ввода, напечатать код/причину и повторить ввод именно этого поля.
7. Вернуть корректное значение.

from_chars сам исключения не выбрасывает: он возвращает код ошибки. Наша функция
преобразует этот результат в собственное исключение для демонстрации задания.
Проверка конца обязательна: 2024abc и 12.5 для целого нельзя принимать как 2024 и 12.
Для дробных чисел предлагается десятичная точка; это нужно явно написать в подсказке.
Допустимость записи с экспонентой согласовать; минимально достаточно обычной дробной.

Марка хранится в собственном String из лабы 2. Для её проверки достаточно длины
и доступа по индексу. Разбор чисел остаётся в модуле Input.

Не утверждаем, что преподаватель имел в виду именно from_chars: в записи название
не установлено. Это подходящий предлагаемый стандартный инструмент.

Каждый пункт меню и каждое поле вводятся с отдельной строки. При ошибке
программа запрашивает только это значение. Числовой разбор проверяет всю строку.

EOF и badbit не должны приводить к бесконечному повтору. Для них InputError
передаётся наружу: EOF завершает диалог, неисправность потока отменяет дальнейший
ввод. Исправимые ошибки формата/диапазона обрабатываются локальным повтором.
Если ошибка относится к состоянию потока, clear не заменяет удаление некорректного
ввода; при чтении токенов с from_chars неверное число уже извлечено как текст.
Пример: последний токен корректен и сопровождается eofbit — значение принимается;
только отсутствие следующего необходимого токена завершает ввод.

## Как изменятся классы и операторы

- Friend operator>> сохраняется. Внутри вместо прямого чтения числовых полей
  используются проверенные функции. Наследник по-прежнему читает базовую часть
  через static_cast и затем собственные поля. Методы read/write не возвращать.
- print_read_info сохраняет подсказку, вызов >> и ковариантный возврат *this.
- change_field использует те же правила ввода. Недоступное для класса поле не
  должно считаться успешным изменением: это ошибка выбора, которую исправляет диалог.
- Сеттеры и конструкторы с параметрами тоже проверяют значения: иначе недопустимое
  состояние можно создать без консоли. Правила должны быть общими, без дублирования.
  Эти проверки выбрасывают ошибку, но не спрашивают ввод и не содержат бесконечных циклов.
- Конструкторы по умолчанию сейчас делегируют параметрическим с «Без марки», 2020
  и положительными числовыми значениями. Например Bus получает 1 место/маршрут,
  Trolleybus — аккумулятор 60.0. Утверждение о нулевых заготовках было устаревшим.
  При валидации решить, остаётся ли «Без марки» допустимой заглушкой с пробелом
  или меняется на согласованную корректную марку. Не вводить случайное исключение
  при любом создании объекта по умолчанию.
- Объект нового ввода не находится в дереве, пока не введены все его поля.
  Существующий объект редактируется через копию. При ошибке/EOF копия освобождается,
  исходный объект сохраняется. Полная транзакционность произвольного прямого >>
  в уже существующий объект — отдельное решение; не обещать её без реализации.

## Как изменится дерево

Минимальная полезная обработка ошибок контейнера:

- operator[] проверяет номер сам до начала продвижения генератора и выбрасывает
  ContainerError при выходе за диапазон. Проверка main может остаться для диалога,
  но больше не является единственной защитой от недопустимого доступа.
- add(nullptr) вместо молчаливого пропуска выбрасывает ContainerError.
- find продолжает возвращать nullptr при отсутствии: обычный безуспешный поиск
  не обязательно исключение. Ошибку вызывает операция, которой необходим найденный
  объект; она проверяет результат, прежде чем вызывать ->remove().
- remove пустого узла может сохранить bool/false; clear пустого дерева — обычная
  допустимая операция. Не делать исключения из каждого штатного результата.
- Дубликаты ключей остаются допустимыми. Порядок и сравнения классов сохраняются.
- iterate пустого дерева по-прежнему даёт пустой диапазон. Готовый std::generator
  и три отдельных дерева сохраняются, новый класс итератора не нужен.

## Исключения и сохранность объектов

Сейчас main сначала удаляет оригинал, затем изменяет копию и добавляет её в дерево.
С появлением исключений такой порядок может потерять оригинал.

Предлагаемый порядок редактирования:

1. Получить копию выбранного объекта и найти узел оригинала до изменения копии.
2. Изменить и полностью проверить копию, оставив оригинал в дереве.
3. Успешно добавить изменённую копию.
4. Только после успешного add удалить сохранённый узел оригинала через remove().

Для текущего add сохранённый указатель на существующий узел остаётся корректным:
вставка не освобождает и не перемещает существующие узлы. Эту узкую гарантию нужно
явно закрепить при реализации; на remove/clear она не распространяется, а генератор
во время вставки всё равно не используется. Это предлагаемое уточнение прежнего
общего запрета сохранять узлы через любые изменения дерева.

При отказе ввода/проверки/выделения памяти оригинал должен остаться. Нужно отдельно
закрепить контракт add: до успешной вставки объектом владеет вызывающий код,
после успешной вставки — дерево. При исключении до передачи владения временный
объект освобождается. Не передавать один указатель дважды и не удалять его после
успешной вставки. Даже без умных указателей пути очистки должны быть явными.
Проверить, что завершающий remove не выделяет память и не выбрасывает исключений.

При появлении исключений также просмотреть String::allocate и присваивание:
сначала успешно выделить новое хранилище, затем заменить старое. Старая строка
не должна теряться или оставаться с висячим указателем при std::bad_alloc.
Не заменять стандартный bad_alloc искусственной ошибкой формата ввода.

| 201 | InvalidIndex | Номер строки вне 0..size()-1 | Отмена операции/повтор выбора |
| 202 | NullObject | В add передан nullptr | Отмена операции |
| 203 | ObjectNotFound | Объект обязателен для операции, но find вернул nullptr | Отмена операции |

Для TextTooLong нужна отдельная явно установленная граница входного текста.
Существующее MAX_LENGTH 80 в String не должно приводить к незаметному принятию
усечённого токена. Зафиксировать, измеряется ли граница в байтах или символах.
EOF и StreamFailure имеют отдельные коды и не попадают в цикл повторного ввода.
Файловые коды предварительно зарезервированы: в текущем проекте файлового ввода/
вывода нет. Наличие FileError в иерархии не означает добавление сохранения/загрузки.
Нужен ли отдельный пример файловой ошибки в лабе 5 — уточнить перед реализацией.

## План реализации после согласования

1. Уточнить папку/ветку, правила марки и границы полей, объём файловой демонстрации.
2. Добавить классы ошибок с кодами, сообщениями и полезными собственными полями.
3. Реализовать общий разбор чисел/марки и функции повторного ввода в Input.h/.cpp.
4. Перевести меню, >> и change_field на проверенный ввод. Читать каждое поле с отдельной строки.
5. Добавить общие проверки в сеттеры и конструкторы с параметрами, согласовать
   значения конструктора по умолчанию и марку «Без марки». Не дублировать правила в каждом месте вызова.
6. Защитить [] и add, сохранить штатные результаты find/remove/clear.
7. Перестроить порядок редактирования и проверить очистку временных объектов,
   владение при неудачном add и исключительную безопасность String.
8. Добавить обработчики там, где можно восстановиться: повтор поля внутри ввода,
   контейнерная ошибка в операции меню, EOF/неисправность потока на границе диалога.
9. Проверить сборки GCC/Clang с включёнными исключениями, предупреждения CLion,
   ASan/UBSan и сценарии ниже. Прежний временный -fno-exceptions для лабы 4 не применять.
10. В отчёте перечислить реализованные коды и показать корректный/ошибочный ввод.
    Не возвращать раздел с описанием реализации и не раскомментировать диаграмму.

Сценарии проверки: буквы вместо числа; 12abc; переполнение; ноль/отрицательное;
дробь вместо целого; nan/inf; границы диапазона; недопустимая/слишком длинная марка;
несколько ошибок подряд с последующим исправлением; EOF в начале и середине ввода;
корректный последний токен при EOF; пустое дерево; недопустимые номера [];
add(nullptr); обычный безуспешный find; неверный выбор поля; ошибка изменения с
сохранением оригинала; повторяющиеся ключи; повторный clear; освобождение копий
при ошибке. Проверить отдельно путь отказа выделения памяти, если он затронут
новым контрактом владения; не заявлять гарантию без такой проверки.
